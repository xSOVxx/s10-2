1. Contexto de la empresa

DeliveryRápido Perú S.A.C.

Cadena de restaurantes con servicio de entrega a domicilio (delivery) en Lima Metropolitana. Maneja altos volúmenes de pedidos en hora punta.

Rubro: Gastronomía · Food delivery
Operación: 12 locales + App propia + motorizados

Situación actual

La empresa tiene 5 sistemas independientes que no se comunican entre sí:

  • App Móvil de Pedidos (nativa Android/iOS)
  • Sistema de Ventas POS (legacy de escritorio)
  • Sistema de Inventario (web propia)
  • Pasarela de Pagos (Niubiz / Izipay)
  • Sistema de Delivery (web propia)

2. El problema actual

Cuando un cliente hace un pedido desde la App, el cajero debe ejecutar tareas manuales que no deberían existir:

Consultar stock

Llamar por teléfono a cocina para saber si hay disponibilidad del plato.

Cobrar manualmente

Pasar la tarjeta por la máquina POS y registrar el voucher en una planilla Excel.

Asignar por WhatsApp

Escribir al motorizado por WhatsApp para que pase a recoger el pedido.

Consecuencias: pedidos duplicados, cobros sin despacho, productos agotados vendidos, reclamos constantes, conciliaciones manuales al cierre del día, pérdida de clientes y de reputación.

Fuente del problema: cada sistema es una "isla" — no comparten información automáticamente. Se necesita un mecanismo de interoperabilidad.

3. Objetivo del arquetipo sistémico

Diseñar la integración de los 5 sistemas a través de una API REST central (API Gateway) que permita el flujo automático de información, garantizando funcionalidad, seguridad y eficiencia.

¿Qué es un "arquetipo sistémico"?

Es un patrón de arquitectura (en este caso, un diagrama de secuencia UML) que define cómo interactúan los sistemas para resolver el problema. Sirve como plantilla reusable para futuros proyectos similares.

Lo que el arquetipo debe permitir

  • Recibir el pedido desde la App y procesarlo sin intervención humana.
  • Validar stock → cobrar → actualizar inventario → asignar motorizado.
  • Manejar excepciones (sin stock, pago rechazado).

Patrón elegido

  • API Gateway centralizada (estilo hub-and-spoke).
  • Servicios Web REST con JSON sobre HTTPS.
  • Reduce integraciones de N × M a N + M.

4. Actores del arquetipo

Son los 6 participantes que intervienen en la interacción, tal como se definen en un diagrama de secuencia UML.

CL

Cliente

Usuario final que realiza el pedido desde la App Móvil.

AM

App Móvil (AM)

Sistema cliente. Recibe pedidos y muestra el estado al cliente.

API

API Gateway (API)

Servicio web REST que orquesta toda la integración. Único punto de entrada.

INV

Sistema de Inventario (SI)

Consulta y descuenta stock de productos/platos.

PAGO

Pasarela de Pagos (PP)

Valida y procesa el cobro con tarjeta (Niubiz / Izipay).

DLV

Sistema de Delivery (SD)

Asigna y notifica al motorizado disponible.

    Cliente->>AM: Realiza pedido (productos, dirección, medio de pago)
    AM->>API: POST /pedidos {productos, cliente, total}
    API->>SI: GET /stock?producto=P001
    SI-->>API: {disponible: true, cantidad: 5}

    alt Stock disponible
        API->>PP: POST /cobrar {monto, token_tarjeta, cliente}
        PP-->>API: {estado: "APROBADO", id_transaccion}

        alt Pago aprobado
            API->>SI: PUT /stock/descontar {producto: P001, cantidad: 1}
            SI-->>API: {stock_actualizado: 4}
            API->>SD: POST /asignar {pedido, direccion, restaurante}
            SD-->>API: {motorizado: "M-014", tiempo_estimado: 25min}
            API-->>AM: 200 OK {id_pedido, estado: "CONFIRMADO", motorizado, tiempo}
            AM-->>Cliente: Mostrar confirmación y tiempo de entrega
        else Pago rechazado
            API-->>AM: 402 {estado: "PAGO_RECHAZADO", motivo}
            AM-->>Cliente: Notificar rechazo del pago
        end

    else Sin stock
        API-->>AM: 409 {estado: "SIN_STOCK", productos_agotados}
        AM-->>Cliente: Informar producto agotado y sugerir alternativas
    end

6. Flujo textual

El Cliente envía el pedido desde la App Móvil con productos, dirección y medio de pago.
La App Móvil invoca a la API mediante POST /pedidos.
La API consulta al Sistema de Inventario con GET /stock.
Si hay stock, la API solicita el cobro a la Pasarela de Pagos con POST /cobrar.
Si el pago es APROBADO, la API descuenta el stock (PUT /stock/descontar).
La API asigna un motorizado en el Sistema de Delivery (POST /asignar).
La API responde 200 OK a la App con id_pedido, motorizado y tiempo estimado. La App lo muestra al cliente.
En caso de fallo (sin stock → 409 o pago rechazado → 402), la API responde con código HTTP estándar y mensaje claro a la App.

7. Criterio 1 · Funcionalidad

¿La API hace lo que debe hacer?

Arquitectura REST

  • Endpoints basados en recursos de negocio (/pedidos, /stock, /cobrar, /asignar).
  • Verbos HTTP correctos: GET (consulta), POST (creación), PUT (actualización).
  • Códigos HTTP estándar: 200, 402, 409, 500.
  • Mensajes en JSON (liviano, estándar de la industria).
  • Bloques alt/else modelan los caminos alternos (stock agotado, pago rechazado).

8. Criterio 2 · Seguridad

¿La API protege los datos y el acceso?

  • HTTPS / TLS en todas las comunicaciones (cifrado en tránsito).
  • Autenticación mediante access_token con OAuth2 / JWT para cada sistema cliente.
  • API Gateway como único punto de entrada → facilita rate limiting y filtrado.
  • Validación de datos en cada endpoint (no confiar en el cliente).
  • Ofuscación: la API nunca expone el token de tarjeta del cliente a sistemas internos.
  • Logs y auditoría centralizados en el Gateway.

9. Criterio 3 · Eficiencia

¿La API rinde y escala?

  • Arquitectura cliente-servidor sin estado (stateless) → cada request es independiente (característica REST).
  • Endpoints cacheables (GET /stock) → reduce carga en el inventario.
  • HTTP/2 para multiplexación y menor latencia.
  • Orquestación centralizada: 1 API Gateway evita conexiones punto a punto (de N × M a N + M).
  • JSON más liviano que XML/SOAP.
  • Webhooks asíncronos para notificar al cliente cuando se asigna el motorizado.

Reducción de acoplamiento

Sin API Gateway:

App ↔ Inventario
App ↔ Pagos
App ↔ Delivery
POS ↔ Inventario
POS ↔ Pagos
POS ↔ Delivery
= 9 conexiones (N×M)

Con API Gateway:

App ↔ API
POS ↔ API
Inventario ↔ API
Pagos ↔ API
Delivery ↔ API
= 5 conexiones (N+M)

10. Respuesta a la pregunta retadora

"¿Cómo lograría usted que dos (2) sistemas empresariales diferentes compartan información automáticamente mediante una API?"
Estandarizar el formato de intercambio (JSON) y los verbos HTTP.
Diseñar endpoints claros basados en los recursos de negocio (no en las bases de datos internas).
Publicar la API detrás de un API Gateway que gestione autenticación, rate limiting y logging.
Versionar la API (/v1/, /v2/) para no romper integraciones futuras.
Documentar con OpenAPI/Swagger para que cualquier sistema pueda consumirla.
Garantizar idempotencia en operaciones críticas (cobros, descuentos de stock) para evitar duplicados ante reintentos.
